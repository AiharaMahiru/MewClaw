# 思维模式与工作框架

本文件确立 dsh-lark 迁移与开发工作的**思维方式**。规则（做什么）见 [AGENTS.md](../AGENTS.md)；本文件回答**怎么想**（如何判断、如何决策、如何自证）。

## 1. 十条核心思维原则

### T1 SPEC 先行，代码是 SPEC 的实现

任何实现动作之前，先有对应 SPEC（格式见 [spec-standard.md](spec-standard.md)）。SPEC 写不下去 = 问题还没想清楚；SPEC 里出现"大概""可能" = 契约有空洞，先补成确定性语句。
顺序永远是：**SPEC → 测试 → 实现 → 证据**。

### T2 证据驱动，不信自述

"应该没问题""看起来对""本地跑过"都不是证据。证据是：类型检查结果、测试结果、快照差异、事件流日志、真实观测。**断言与证据一一对应**；找不到证据的断言降级为开放问题。

### T3 能力缝纪律：定义 / 提供 / 消费三视角

动手前先问三问：

1. 这个能力 dsh 已经提供了吗？（查 `docs/reference/cfg_zh.md` 的插件目录与已安装包清单）
2. 如果自建，Service Definition 的稳定面是什么？谁提供？谁消费？
3. 提供者与消费者是否独立演进？（不独立就合并角色，不硬拆）

复用先于自研；自研前必须写下"dsh 为什么不能胜任"。

### T4 不变量先行，先拒绝后接受

设计顺序：先写**安全与行为不变量**（断言式），再写实现。每条不变量都要能对应一条"拒绝用例"——测试不是证明代码对，而是描述**什么行为算错**。写测试时问：如果这个测试被删掉，什么错误会漏过去？

### T5 失败闭环：每个异步/网络/持久化路径都想一遍失败

写任何一段代码前，默念失败清单：调用方会死吗？响应会重复吗？重启后状态一致吗？超时了怎么办？权限被拒了怎么办？上游返回垃圾怎么办？
要求：**fail loud 优先**；任何静默降级必须显式写名并说明理由（写进 SPEC 失败模式表）。空 catch 必须说明吞的是什么、为什么没有别的可能。

### T6 最小可逆步

每一步独立可验证、可回退、不留半迁移状态。禁止"先都搬过来再慢慢修"——每一步结束，仓库都要处于可测试、可通过门禁的状态。

### T7 对抗性自查

完成前，扮演最恶意的使用者与最倒霉的运行环境质问自己：

- 最坏输入（超大、超长、畸形、注入文本）会怎样？
- 并发（两个请求同时到、重启与请求竞态）会怎样？
- 谁能越过我的授权检查？哪一步把不可信值当成了证据？

重要结论请独立子智能体复核（fresh eyes），不接受"我复查过自己"。

### T8 显式优于隐式，对称优于巧合

- 默认值在拥有实现的边界处显式 resolve，不藏在 `?? default`；
- 两个看起来平行的值写法不对称 = 大概率漏了抽象；
- 命名直指事实（写 `response fields` 而非 `response shape`；`contract` 只用于真正的契约）。

### T9 类型即文档，边界即校验

- 跨边界 ID 一律品牌化（`Branded<B>`），裸 string 不过边界；
- 判别联合必须 switch 穷尽（closed 用 `assertNever`，open 落文档化 default）；
- 运行时校验只放在：解析/配置、队列、模型/工具 JSON、持久化/文件、worker、进程、wire 边界——同进程静态类型能保证的地方**不加**防御代码。

### T10 模型可见 ⟺ 已落盘

凡是能进入模型请求的内容，必须能从 session log 重建。新增任何模型可见输入，同一变更里必须有承载它的 session 事件。

## 2. 工作模式（按任务类型切换）

### 设计模式（做架构决策）

1. 写清 **forces**（要满足的约束，逐条编号）；
2. 列出 ≥2 个候选方案，各写代价；
3. 选一个，写成 ADR（编号、状态、上下文、决策、后果）；
4. 把 ADR 的契约面落进 SPEC。

没走完这四步的"设计"不算设计，只算直觉。

### 实施模式（写代码）

1. 取 SPEC（状态须 ≥ accepted）；
2. 把 §8 测试契约翻译成测试骨架（先红）；
3. 最小步实现（步内只动一个包）；
4. 每步跑**针对性**门禁（该包测试 + 类型 + lint），不做全套；
5. 收尾：SPEC 状态更新 + 证据归档。

### 评审模式（审查产出，含自我评审）

1. 逐条对照 SPEC 契约核对实现；
2. 专找三样东西：**不对称**（平行值写法不一）、**遗漏失败模式**（§5 清单没覆盖的路径）、**过度实现**（超出 SPEC 边界的代码）；
3. 挑战每处"看起来合理"——要求给出理由或测试。

### 调试模式（追问题）

1. 复现（没有复现步骤的修复不是修复）；
2. 最小化输入；
3. 沿证据链找根因（事件流 / 日志 / 类型），修根因不修表象；
4. 补一条"此问题若复发必然变红"的回归测试。

## 3. 决策与分歧

- 决策记录 = ADR（`docs/adr/`，编号连续）；蓝图 §4 的 12 条即 ADR-1..12 的摘要载体，细化时以 ADR 文件为准；
- 分歧解决顺序：SPEC/ADR 原文 → 蓝图原则 → 本文件原则 → 讨论 → 改文档（先改文档再改代码）。

## 4. 反模式清单（发现即修）

| 反模式 | 表现 | 正确姿势 |
| --- | --- | --- |
| 提前泛化 | 为"以后可能"引入抽象 | 等第二个真实用例出现再抽象 |
| 双份真相 | 同一事实两处维护 | 单一 home；其余处引用 |
| 隐藏默认 | 调用方不知道默认值 | 显式 resolve 步骤 + SPEC 记录 |
| 先取后滤 | 检索后再过滤 ACL | 过滤进查询谓词（安全不变量） |
| 宣称未验证的隔离 | "工作目录分开=沙箱" | 逐项证据（路径/符号链接/进程/挂载/网络） |
| 静默跳过 | catch 后当无事发生 | fail loud；降级显式写名 |
| 半迁移状态 | "先搬过来，后面修" | 最小可逆步（T6） |
| 重复造轮子 | 没查 dsh 目录就自研 | T3 三问 |
| 沉重依赖 | "小功能引了个全家桶" | 依赖预算（AGENTS.md 规则 12）；默认可选挂载 |
| 无注释代码 | 读不懂的"简洁" | 完善中文注释（AGENTS.md 规则 11）；注释解释"为什么" |
| 自述式验证 | "本地跑过"代替证据 | T2 证据驱动 |

## 5. 质量门禁速查

| 门禁 | 何时跑 | 依据 |
| --- | --- | --- |
| 包级测试 + typecheck + lint | 每个最小步 | 针对性，不做全套 |
| 全套测试 | 里程碑收尾 / CI 诊断 / 全局性变更 | [测试策略](../docs/reference/dsh-AGENTS.md) |
| 快照 | 任何模型可见 / 用户可见输出变化 | 键无密钥重放 |
| 安全拒绝用例 | 任何授权/隔离/ACL 变更 | T4 |
| 证据归档 | 里程碑验收 | `docs/evidence/` |

## 6. 评审清单（每次交付前自问）

1. SPEC 状态与实际代码一致吗？
2. 有没有超出 SPEC 边界的实现？
3. 失败模式表有没有漏掉的新路径？
4. 每个断言都有证据吗？
5. 有没有把不可信值当证据？
6. 有没有可删的代码（迁移遗留、临时方案）？
7. 文档和代码同 PR 更新了吗？
8. 依赖有预算吗（新增依赖的必要性写进 SPEC 了吗）？
